# ADR-H-001 — Generalize the harness into core/configuration/workspace layers

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner (mission) / Architect (proposal)
- **Context:** The harness was built around one specific client project. Stack, domain, GitHub identity, ID prefixes, and deploy CLIs were hardcoded across agents, config, templates, and docs, so any second project required manual surgery.
- **Decision:** Split into Layer A **core harness** (`harness/` kit + `docs/harness/` specs — never project-specific), Layer B **project configuration** (`project.yaml` — the single per-project input), Layer C **project workspace** (`docs/project/`, code, generated instance files). Instance files are generated artifacts; rules change only by editing the kit and owner-applying.
- **Consequences:** upgrades propagate mechanically; doc/config drift is detectable; project work can never contaminate the core; one more generation step (mitigated by init/apply scripts). The originating project becomes an example instance, not the foundation.
- **Supersedes:** implicit project-coupled structure of the 2026-11-04 baseline.

# ADR-H-002 — Kit templates with `{{PLACEHOLDER}}` substitution rendered from project.yaml

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Architect (routine)
- **Context:** Templates must render for arbitrary stacks without YAML-parsing complexity in Windows PowerShell 5.1 (no `utf8NoBOM`, no parser module, dependency restrictions).
- **Decision:** Plain-text templates with `{{TOKEN}}` substitution + a constrained project.yaml subset parser (flat keys, inline arrays, indentation sections). Render slots inject whole rule blocks (agent command lists, MCP denies, policy items). Unresolved tokens after render = hard failure (leak detection). Output is UTF-8 **without BOM** (PS 5.1 `Set-Content -Encoding UTF8` writes a BOM; use .NET `File.WriteAllText`).
- **Consequences:** zero external dependencies; deterministic output; format discipline on project.yaml; parser documented limits accepted (complex structures are not needed).
- **Alternatives rejected:** powershell-yaml (dependency), full JSON config (worse comments/human editing), PowerShell classes (5.1 friction).

# ADR-H-003 — Lifecycle: seven phases with owner-approved profiles for tailoring

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner (mission mandates full lifecycle + tailoring)
- **Context:** The approved baseline covered six phases ending at Deployment. The mission requires ongoing maintenance coverage and forbids forcing every project through every phase.
- **Decision:** Canonical phase set = Discovery, UI/UX Design*, Architecture, Development, QA, Deployment, **Operations & Maintenance (steady state)**. Five profiles (full/lean/headless/brownfield/micro) select active phases; selection is an owner decision recorded in `project.yaml` and rendered into `phase-state.md`; skips stay visible with justification; governance (gates, OD-18, evidence) is identical across profiles.
- **Consequences:** covers idea→operations without ceremony inflation; operations phase formalizes `/ops`, incidents (OD-20), upkeep rhythms; profile table is the single tailoring mechanism.
- **Preserves:** all six original gates and OD-18 material rules.

# ADR-H-004 — `policies` as the delegation-proof hard-deny layer

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Architect (mission: enforcement must survive delegation/shell)
- **Context:** OpenCode permission rules are ordered with last-match-wins and agent rules append **after** project rules — an agent allow silently re-opens project denies (observed: `firecrawl_*`). `--auto` auto-approves anything not denied; saved approvals are project-wide allows.
- **Decision:** Two-tier enforcement: (1) **permissions** layer — deny-by-default shell/delegation/skills/MCP + per-role allow-lists for routine scope; (2) **policies** layer (`tool.use` hard denies, evaluated after permissions + saved approvals + agent rules) for everything irreversible or authority-bearing: dangerous git, GitHub authority verbs, shell write-cmdlets, nested runtimes, publishing, secret-read shapes, plus project `deploy_commands`/`hard_deny_commands`. Agents never allow-list anything the policy layer denies. `validate-harness.ps1` FAILs any agent that re-allows denied MCP classes.
- **Consequences:** governance boundaries cannot be bypassed by configuration drift, delegation, or approval fatigue; policy semantics are version-dependent → re-verified by negative-test matrix each upgrade.
- **Alternatives rejected:** guardrail plugin (OD-16 forbids without proven gap; native policies close the gap); relying on agent prompts (not enforcement).

# ADR-H-009 — Feature-branch pushes: permission-scoped, not policy-blanket

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Architect (routine, correcting audit-time draft)
- **Context:** A first-pass policy denied `git push *` wholesale, which would also break the approved Developer feature-branch push. The over-broad `git *push*` wildcard also false-positives on benign commands (`git add push.js`).
- **Decision:** Push control split: permission layer denies all push; Developer agent allow-lists explicit `git push [origin|-u origin] <feature-prefix>/*`; policies hard-deny only irreversibility shapes (`--force`, `-f`, `--delete`, `--mirror`, protected refs, `git.exe` variant, `reset --hard`, `clean`, `branch -D`, `filter-branch`). GitHub-side protection remains the final control.
- **Consequences:** least privilege without breaking the approved workflow; no wildcard false-positive hazards; N-10/N-11 negative tests pin behaviour.

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner
- **Context:** The kit was developed inside a client repository while that project was its only instance. Layer A (core harness) and Layer C (one project's workspace) shared a tree, and the generalized kit still referenced `docs/harness/` as canonical while holding no copy of it.

# ADR-H-011 — Kit self-test is the development gate; script sources must be ASCII

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Architect (from defects found by running the kit)
- **Context:** Building the first automated check for the kit exposed that nothing had ever run it end to end. Five defects were live simultaneously: (1) `lib-render.ps1` contained `U+2192` in BOM-less UTF-8, so Windows PowerShell 5.1 decoded it through the ANSI codepage into bytes containing an apostrophe and refused to parse the file — the scripts were unrunnable on the platform the kit claims to support; (2) a stray quote in `Get-StackPolicyDenies` broke parsing independently of encoding; (3) `New-RenderContext` read `HARNESS-VERSION` from inside `kit/`, where it does not live; (4) `init-project.ps1` overwrote `$Target` with `Resolve-Path`, which returns nothing for a directory that does not exist yet, so creating a new project always failed; (5) `lib-apply.ps1` stripped the 5-character `.tmpl` suffix by removing 6 characters, so every generated file lost its last extension letter (`business-analyst.m`, `bug.ym`, `phase-state.m`) and downstream checks silently skipped rather than failing.
- **Decision:** `tests/check-sources.ps1` (static: ASCII-only script sources with no BOM, tokenizer parse of every script, every template slot must have a producer, kit contract asserted by filename and count) plus `tests/render-and-validate.ps1` (renders a throwaway instance per lifecycle profile and for the all-integrations variant, asserts artifact names/counts/toggle effects, then requires `validate-harness.ps1` to exit 0 **and** to have recorded specific `[PASS]` markers). `.github/workflows/kit-validation.yml` runs the render test and the static policy on Windows, Linux and macOS. Glyphs needed in rendered output are emitted from code points, never as source literals.
- **Consequences:** template and renderer edits are verified before merge; a validator check that errors out can no longer masquerade as a pass (marker assertions); the harness gains a reproducible development loop it did not previously have. The renderer originally addressed files with Windows separators, so instance rendering was exercised on Windows only until 2026-11-10, when the literals were converted to forward slashes and the render job was widened to all three platforms.
- **Rejected:** trusting exit codes alone (an errored check records nothing); scanning all instance files for placeholder leaks (the kit's own scripts and core docs legitimately contain token syntax — the sweep is now scoped to generated files).

# ADR-H-012 — `/improve-harness` makes the harness-change proposal path explicit

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner
- **Context:** The PM already had a duty to "propose harness improvements as issues, never as direct edits" and the kit shipped a `harness-improvement` issue form, but no command walked anyone through the proposal. Observed friction therefore either went unrecorded or arrived as an under-specified issue with no evidence, no named kit file, no classification, and no statement of what would prove the change works. Separately, the AI BA Harness reference shows a `/improve-harness` that distinguishes a *project setting* from a *kit change* before proposing anything — the distinction our commands left implicit.
- **Decision:** Add `harness/kit/commands/improve-harness.md.tmpl`, bound to `project-manager` (PM commands do not set `subagent: false`, per OD-03). It interviews at most three questions with concrete examples, requires a duplicate check against the decision register, `open-decisions.md`, `adr/`, and open `type:harness-improvement` issues, classifies the change (doc-only / template / permission-policy-governance / renderer) and maps that class to a version bump and whether an ADR is required (OD-18), then writes the proposal to `docs/project/working/project-manager/harness-feedback/<yyyymmdd>-<slug>.md` and drafts the issue body, creating the issue only on the owner's explicit yes. It never applies anything, and explicitly refuses to propose weakening a permission, policy, gate, or approval as a convenience — recording "this control is working as designed" is a valid outcome.
- **Consequences:** command count 15 → 16, asserted by `check-sources.ps1`, `render-and-validate.ps1`, `validate-harness.ps1` and `check-site.ps1`; `AGENTS.md.tmpl`'s PM row now also lists `/init-project`, which was previously omitted from that table while existing as a PM command; the PM duty line now names the command. Proposal path deliberately sits **inside the PM's existing `docs/project/working/project-manager/**` write scope** rather than a new `harness-feedback/` root, so no permission rule had to be widened — the same argument that made the site's honesty section note agents cannot edit governance paths.
- **Rejected:** a separate `/setup` command (would duplicate `/init-project`, which already conducts the interview, diffs `project.yaml`, and waits for the owner); writing to `harness/staging/` from an instance (staging is an apply-time area of the kit home repo, and `docs/project/working/` is where non-authoritative material belongs per ADR-H-005); adding a `docs/project/working/harness-feedback/**` allow-rule (widening the permission layer for a convenience the existing subtree already provides); letting the command patch the instance's local `harness/kit` copy as a trial (that is `apply-harness-change.ps1`'s owner-authorised job, and a locally-patched kit is exactly the drift ADR-H-006 exists to prevent).

# ADR-H-013 — Provenance is attested or preserved, never inferred from wherever git happens to be

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Architect (from a determinism assertion that failed)
- **Context:** `KIT_COMMIT` was resolved by running `git rev-parse` in the directory holding the kit copy. Inside a rendered instance the kit is a *copy* inside the instance's own repository, so git reported the **instance** commit and stamped it as kit provenance. Two instances built from one kit therefore claimed different provenance, and re-applying an upgrade rewrote the stamp - which surfaced as a "rendering is not deterministic" failure once the self-test actually exercised `apply-harness-change.ps1`. The same audit found the interactive path never substituted `{{KIT_COMMIT}}` at all, so every instance created through the documented `/init-project` interview shipped a literal placeholder in its own `project.yaml`, later reported by the kit's own validator. A third finding was structural: `labels.json` was commented YAML consumed by `ConvertFrom-Json`, so `sync-labels.ps1` had never been runnable.
- **Decision:** Three rules, enforced rather than described. (1) **Provenance resolution order:** inside an instance carry forward the `rendered_from_commit` it already recorded; otherwise attest from the kit repository, and only when that repository's root has no `project.yaml` (so it is a kit home, not an instance); otherwise `unknown` - the silent `'local'` fallback is gone. (2) **Record and artifacts cannot disagree:** `init-project.ps1` writes the resolved commit and kit version into the instance's `project.yaml` after rendering, and the self-test asserts both stamps and that no unresolved placeholder survives. (3) **Reachability is audited against the renderer itself:** `tests/check-sources.ps1` calls `Get-RenderPlan` and requires every file under `harness/kit/` to be either rendered or a declared non-rendered input with a stated reason; `kit/**/*.json` must parse as JSON; and `project.yaml.tmpl`'s slots are audited against the interview's producer set, since that file is substituted by `init-project.ps1` rather than by `Expand-Template`.
- **Consequences:** re-apply is idempotent, proven rather than promised; a template that ships but is never generated now fails the build; the guided onboarding path produces a self-consistent `project.yaml`; and a kit copy transported without git honestly records `unknown` instead of inventing a hash.
- **Rejected:** resolving `KIT_COMMIT` from the instance's HEAD (attributes instance commits to the kit); any timestamp-derived substitute (provenance must identify content, not a build moment); continuing to copy `project.yaml` verbatim (two provenances in one instance, and the wrong one survives re-apply); hand-maintaining a list of rendered files in the test (it would drift from `Get-RenderPlan`, which is the thing under audit).

# ADR-H-014 — The kit home repository adopts the governance it ships

- **Status:** accepted, partially implemented (see Consequences) · **Date:** 2026-11-09 · **Decider:** Owner
- **Context:** The kit preaches issue forms, owner-only merges, CODEOWNERS review on governance paths, private security reporting, and a decision record per material change - while this repository had none of them. `.github/` held two workflows; `main` had no protection; there was no `CODEOWNERS`, no intake form, no security policy, no `CONTRIBUTING.md`, no `CHANGELOG.md`, and no tag for any of the three versions published. The handbook therefore documented controls this repository does not exercise - the doc-drift class ADR-H-008 exists to prevent.
- **Decision:** Adopt the kit's own artifacts here: `.github/ISSUE_TEMPLATE/` with `bug` and `harness-improvement` forms plus a `config.yml` that disables blank issues and routes security reporting to a private advisory; `.github/CODEOWNERS` (`* @tauhid-sifat`); `.github/CONTRIBUTING.md` (layer rules, the ASCII-source rule, "never widen permissions for convenience", approved-is-not-verified, and the two local gates); `.github/SECURITY.md` (threat model is a confused or tricked agent, in-scope and out-of-scope lists, "a failing test beats a description"); `CHANGELOG.md` required for every `HARNESS-VERSION` bump; and git tags plus GitHub Releases per version so `kit_version` and `rendered_from_commit` point at something a consumer can pin.
- **Consequences:** what the handbook claims about this repository is checkable rather than aspirational, and a contributor meets the same intake path an instance does. **Deliberately not done:** branch protection with required checks, and a `LICENSE`. Branch protection changes how this repository is worked - direct pushes to `main` stop working, which is exactly what the kit forbids inside an instance - and licensing is the owner's legal decision; both remain open in the handbook's honesty table.
- **Rejected:** copying all 11 instance issue forms here (requirement, phase-gate, QA and refactor forms describe product work that never happens in a kit repository); publishing the owner's personal email as a security contact (private advisories need no address); enabling branch protection silently inside a code change, which is the pattern the harness itself calls a material change made without approval.

# ADR-H-015 — Skill grants are project configuration; `project.yaml` is the authority

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner
- **Context:** The agent templates hardcoded 42 skill allow-list entries (`to-spec`, `grill-me`, `wayfinder`, `ask-matt`, `hallmark`, `tdd`, …) and `validate-harness.ps1` carried a 24-name snapshot of "known globals" to decide whether a grant was real. The result was 41 identical warnings on every fresh instance, which made a genuinely missing skill indistinguishable from inventory noise, and it meant the core kit encoded one person's machine. It also contradicted the kit's own layer rule: skill IDs are instance-specific, as `skills-inventory.md` §2 already said.
- **Decision:** The kit ships no skill grants. `project.yaml` declares them (`skills.shared`, `skills.<role>`, plus `stack.agent_skills` for the Developer). `Get-RoleSkillGrants` in `lib-apply.ps1` resolves the effective map - declared values first, then what the integration toggles imply (`hallmark`/`impeccable` under `design_system_tools`, `browseros-neo` under `browser_live`, the Designer's `prototype`/`writing-for-agents` baseline) - and it is the only source, consumed both by the renderer and by `validate-harness.ps1`. The validator now **fails** an agent granting a skill outside the map and **warns** only for a declared skill that is not installed; `globalKnownSkills` is deleted. `skills:declared` and `skills:installed` became required PASS markers, and the self-test installs a stub `SKILL.md` per granted skill so "declared and installed" is an assertion rather than an environment accident.
- **Consequences:** a new project can use the kit without inheriting anyone's tooling; a missing skill becomes visible because it is the only warning left; the render/validate pair share one authority so a grant cannot exist in the instance and be assumed by the check; the interview gained one prompt (shared skills) while per-role lists stay a `project.yaml` edit.
- **Verification:** rendering from `HEAD` and from the working tree was compared per role - all 7 grant sets identical. The comparison earned its keep: the first version put three skills in `skills.shared` and over-granted six roles.
- **Rejected:** keeping a curated default list in the kit (re-creates the environment leak the change exists to remove); letting agents resolve skills at runtime (removable only by a rule the runtime enforces, not by prompt); validating against a maintained global snapshot (a second copy of the truth, which is what broke before).

# ADR-H-016 — A machine-readable verification ledger, consumed rather than read

- **Status:** accepted · **Date:** 2026-11-09 · **Decider:** Owner
- **Context:** The harness's founding rule is approved ≠ implemented ≠ verified, but the statement of which is which lived in prose: audit tables in dated documents, a handbook section, and my own `check-site.ps1` assertions that specific sentences exist. Prose can be deleted politely, inflated quietly, and cannot be joined against anything. Meanwhile the runtime protocol had 34 named tests with no mapping to the controls they prove, so "we run the matrix" and "the matrix covers the promises" were unverifiable claims - and the kit itself was making them.
- **Decision:** `docs/harness/verification-ledger.json` (schema `aidlc.verification-ledger/1`) is the single record: each control has an id, a tier, one of exactly three statuses, evidence entries typed `check|ci|run`, and the runtime tests that would prove it. Three consumers, no hand-editing path around them: `validate-harness.ps1` loads it inside every instance and FAILs a `verified` row without evidence, reporting the status mix on each run; `tests/check-sources.ps1` enforces the schema, unique ids, the vocabulary, and a two-way join with `negative-tests.md` (a citation must exist; a test claimed by no control fails too); `tests/check-site.ps1` requires the handbook's stated counts to equal the file's computed counts. Only `verified` requires evidence, and evidence must name something that can be looked at - a check, a CI run, or a recorded execution.
- **Consequences:** 31 controls, 6 verified, 19 implemented, 6 designed. The ledger is deliberately unflattering: VC-11, the assumption that policies evaluate after permissions and saved approvals - the thing the whole enforcement story rests on - is `designed`, because no live session has ever demonstrated it. Adding a control without evidence cannot pass CI, so the temptation to inflate has a mechanical answer. Runtime work becomes a queue rather than a mood: run a case, attach the run, move the status.
- **Rejected:** prose with a checklist (already the status quo, and it drifted); generating the handbook section from the ledger at deploy time (needs a build step and a templating dependency the site deliberately avoids - instead the numbers are asserted equal, which catches drift without machinery); marking controls verified on the strength of static checks (the checks prove configuration, so the controls describing runtime behaviour stay `implemented`); a Markdown table as the source format (parseable, but joinable against nothing).

# ADR-H-017 — Layer A purity vocabulary is derived from project.yaml, not hand-maintained

- **Status:** accepted · **Date:** 2026-11-10 · **Decider:** Owner
- **Context:** The Layer A purity check (VC-25) enforces that the harness never names a project or inherits its domain vocabulary. It works, and it made the 1.2.1 generalisation stick. But the terms it looked for were six literals assembled from code points in the checker itself. A *new* project leaking its own client name, domain noun or internal codename into the kit would pass, because the checker only knew the names it had been told.
- **Decision:** Two complementary, opt-in sources extend the fixed backstop, neither readable in the checker: a `--Terms <file>` parameter (one term per line) and a `project.yaml` (via `-ProjectYaml`, defaulting to a `project.yaml` at the repository root) whose `project.name`, `project.slug`, `project.description` and `data_policy` label are read and banned from Layer A. The fixed backstop stays, assembled from code points, and the positive control that proves the scanner sees a violation before silence is trusted stays. Derived terms scan Layer A only: a `project.yaml` committed under `tests/` or `examples/` legitimately names itself, so those trees are skipped for derived terms (the backstop still scans everywhere).
- **Consequences:** adding a project identity to a kit template now fails the build by pointing the check at that project's config, without editing the checker. The kit home repository's own CI supplies neither source, so there it still relies on the fixed backstop; a developer adapting the kit for a project passes that project's `project.yaml` or a `--Terms` file to close that loop.
- **Rejected:** inferring the vocabulary from `examples/*.yaml` (those are starter configs whose names are shared with the handbook's worked example, so banning them would self-flag `site/`); word-splitting the name and slug into individual tokens (generic words such as "Kit" or "Console" would false-positive across the docs); adding a `data_policy.label` field (the label already surfaces inside `data_policy.rules` and is extracted there).

# ADR-H-018 — Application source is edit-denied project-wide; only the Developer re-allows it

- **Status:** accepted · **Date:** 2026-11-10 · **Decider:** Owner
- **Context:** A runtime audit (N-02) showed the project-manager could edit `src/example.js`. The permission model was *allow-by-default for edit*: the base `{ "action": "*", "resource": "*", "effect": "allow" }` was followed only by denies on governance paths, so application code (and tests, and root files) was editable by **every** role. That contradicted `agent-specifications.md` ("the reviewer has `edit **` otherwise denied - zero domain write scope"), `repository-structure.md` ("application code ... approved roles within their scopes") and negative test N-02, and silently voided the orchestrator write-scope claim (VC-31).
- **Decision:** The project layer now renders an `edit <source_dir> deny` for every `stack.source_dirs` entry (`src/**`, `tests/**` in the examples). The Developer agent alone re-allows those directories (`{{DEVELOPER_SOURCE_ALLOWS}}`), so it can still write code and unit tests; every other role - orchestrator, BA, designer, QA, reviewer, security - is denied application code unless it has an explicit allow. `validate-harness.ps1` gains `config:source-deny:<dir>` (FAILs when the deny is missing) and `render-and-validate.ps1` asserts the config denies `src/**`, the developer allows it, and the PM does not.
- **Consequences:** the documented write-scope model is now real for application code, not just for `docs/project/**`. Verified live on OpenCode 2.2.6: project-manager edit of `src/example.js` returns `Permission denied: edit`; the developer's edit of the same path succeeds. Root files and non-source paths remain at the base allow (they are neither application code nor governance), so a future role grant for them is still a deliberate agent-level allow.
- **Rejected:** denying `edit **` outright (the Developer also edits docs/project/architecture and working notes, and every project carries root config such as `package.json`; `edit **` would require enumerating every non-source file and break legitimately); adding the denies only to the non-developer agents (source dirs are project-specific, so a `src/**` literal would miss a project whose code lives in `app/`).
