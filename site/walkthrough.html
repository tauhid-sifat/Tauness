    Acme Console, start to finish

    One worked example of the AIDLC Harness: a real configuration, the commands you would type, what each step produces, and where you stop and decide. The project is fictional. The commands, file counts, generated filenames and validation results are what the shipped kit actually does on this machine.

    Read the handbook for what things are for; read this page for how a project actually goes. Where a claim depends on runtime behaviour that has never been demonstrated, this page says so - the list is in What is not yet proven.

    The project

    Acme Console - a customer-facing web app: marketing pages, a booking flow, and an admin area for support staff. Next.js App Router with Supabase (Postgres and auth), deployed on Vercel. One owner, a handful of agents. Support and finance data makes it personal-sensitive. It starts from the kit's examples/nextjs-web.yaml, which is full profile - all seven phases.

    DecisionValueConsequence
    Lifecycle profilefullDiscovery, Design, Architecture, Development, QA, Deployment, Operations - each owner-gated
    Areasweb, booking, admin, cms, auth, data, infra, docsEach becomes an area: label; issues must pick one
    ID prefixACMEvery artifact is addressable: ACM-REQ-014, ACM-TC-007, ACM-DEC-003
    Deploy CLIsvercel, supabaseDenied in the permission layer and hard-denied in policies - no deploys from a laptop, by agent or by accident
    Data sensitivitypersonalEvery agent carries the sentence that personal data stays inside Git and approved tools; web research renders as deny, not ask
    Model readinessgated at firstPropose-only until the owner verifies provider privacy; flip to verified deliberately

    Day 0 - adopt the harness

    Twenty minutes, mostly reading. Plan it as part of the first working day, not as a ritual afterwards - a project adopted late has no decision register and no traceability for the decisions already made.

    git clone --branch v1.3.0 https://github.com/tauhid-sifat/Tauness.git harness-kit
copy harness-kit/examples/nextjs-web.yaml ./acme-console.yaml
notepad acme-console.yaml            # name, slug, prefix, owner login, areas, models, readiness
pwsh -File harness-kit/harness/scripts/init-project.ps1 -Target ../acme-console -Config ./acme-console.yaml

    The render prints its plan first if you add -DryRun; without it, it writes new files, skips anything already present, and reports conflicts rather than overwriting. What lands (measured):

    root                     5   AGENTS.md, opencode.jsonc, project.yaml, .gitignore, README.md
.opencode/agents         7   project-manager, business-analyst, designer, developer, qa-engineer,
                              code-reviewer, security-monitor
.opencode/commands      16   8 PM-run, 8 specialist-run
.github                 17   11 issue forms + config, 4 workflows, labels.json, CODEOWNERS, PR template
docs/project            18   seven phase dirs, knowledge base + templates, decision register,
                              phase-state, traceability, working notes
docs/harness            20   copied: specifications, ADRs, dated evidence, verification ledger
harness                 75   copied: the kit, so upgrades can be re-applied inside this repo

    The generated AGENTS.md is stamped with what it came from, which is what makes an upgrade reviewable later:

    > **Status:** Owner-approved harness instructions - Generated 2026-11-09 from harness kit 1.3.0 (commit e20aaca).

    Then read two files before writing any code. opencode.jsonc is the complete list of what the agents may run - it is shorter than people expect. docs/project/status/phase-state.md says where you are, and a fresh instance starts honestly before Phase 1:

    current_phase: "0-harness-setup"
status:        not_started
profile:       "full"
    cd ../acme-console
pwsh -File harness/scripts/validate-harness.ps1          # 57 PASS / 0 WARN / 0 FAIL
git init -b main; git add -A; git commit -m "Initialize from AIDLC harness 1.3.0"
gh repo create acme-console --private --source=. --remote=origin --push
pwsh -File harness/scripts/sync-labels.ps1 -Repo you/acme-console

    Then do the part only you can do. Branch protection on main, CODEOWNERS review required (the file is already generated), a production Environment with you as required reviewer. Until those exist, everything the harness enforces is enforced by OpenCode's config on your machine - which is the level of protection the ledger calls implemented, not verified. sync-labels.ps1's gh label create path is attested against a live repository but has never been run in CI, so read its output the first time.

    Phase 1 - discovery, and the first knowledge

    Open OpenCode in the repository. One command starts the phase, and it does not start building.

    /status
/pm Bookings must not double-book a technician; support needs to see why a booking changed

    /pm restates the goal with a definition of done, checks the phase, profile and decision register, and opens Discovery issues. Then the material arrives through /intake - the kickoff notes, the support backlog, whoever's spreadsheet:

    /intake docs/project/working/business-analyst/inbox/2026-11-09-kickoff.md

    Nothing is written to the knowledge base yet. Five things happen, and the fourth is the one that costs you time:

    extract, each item quoted→judge against the KB→stage a proposal file→critic, read-only, fresh context→you, item by item→apply + commit

    Each staged item carries a verdict, which is the discipline the whole knowledge base rests on:

    VerdictExample from the kickoff notesWhat happens
    new"a booking can be moved by support without a reason only under 15 minutes"Becomes a business rule on a capability page once you accept it
    confirmsthe existing ACM-CAP-002 behaviour, restatedAdds the kickoff note as a source; no new rule
    contradictsa stakeholder says category-A waits escalate in 2 hours, a confirmed rule says 4Nothing is overwritten. It becomes an open question to the owner of that rule, and the confirmed text stands
    answersthe question the gate issue has been carryingThe question is marked answered, with the quote and speaker
    duplicate / extendsthe same rule from a second document; a narrower case of an existing oneMerged as a source, or written as a new rule linked to the old one

    Authority is checked, not assumed. The scheduler's sentence becomes ACM-DEC-003 because stakeholders.md says that role decides booking rules; the pilot customer's wish for two hours becomes a question, because they do not. A second-hand "we agreed it at stand-up" keeps a page at confirmed, never approved.

    The critic is the reviewer agent, delegated read-only by the BA - the one thing in the flow that reads the batch with fresh eyes. It finds missing items, quotes that do not match, authority not checked, and data that should be redacted. It never approves. Its notes go on top of the file, above your tickboxes.

    /ask is the read side, and it is the reason to let the rest of the team clone this repository:

    /ask what decides whether a booking escalation goes to the depot channel?

    Cited pages, statuses shown, draft marked as unconfirmed - and when the project genuinely does not know, it says so and drafts the question for the right person instead of filling the gap with something plausible.

    The first gate

    When Discovery looks finished, the PM packs the evidence; it does not close the phase.

    /phase 1-discovery

    You get docs/project/status/gates/1-discovery-booking-rules.md: a criteria table with a reproducible link per row - command and output, CI run, review thread, artifact path, screenshots only where the criterion is visual - plus unresolved risks, stated assumptions, and one explicit decision request. It opens a phase-gate issue and sends a pull request that moves phase-state.md to awaiting_approval on phase/1-discovery.

    approved_by and approved_at are not for the agent to fill. Those two fields are set by your merged commit and nothing else, which is the whole design in two column names. If a gate is missing evidence, the command marks the gate blocked and stops instead of dressing up a weak pack.

    Phases 4 and 5 - build it, then verify it independently

    /plan breaks the approved scope into dependency-ordered items, each tagged with a change class. Class A is internal - no approval, PM checks evidence. B and C are material requirements and material architecture or security changes, and they stop for you before implementation. D is the emergency path.

    /dev ACM-REQ-014 - support can reassign a booking within 15 minutes without a reason

    The developer works on feat/14-reassign-window, writes tests, and opens a PR that must satisfy the generated policy check: a Closes # line, a Req: reference or an explicit Req: N/A, plus type: and phase- labels. It can push its branch. It cannot merge. If the change alters an architectural commitment, it stops and proposes an ADR instead of quietly deciding.

    /review 41        # advisory verdict on the diff; no edits, no approval
/qa            # independent verification of ACM-AC-021 against preview, with evidence
/security      # only because the diff touches auth and support access to other people's bookings

    QA cannot fix what it tests, and cannot reach production - its fetch rules allow localhost and preview and deny the public internet. The reviewer has no write scope outside its own working folder at all. Neither can approve: they produce verdicts, you produce the merge.

    A material change, mid-flight

    Two weeks in, finance asks that the escalation window be configurable per depot rather than fixed. That is material by definition - it alters a business rule and a data-shape commitment - so it cannot be handled as a nice tweak inside an open story.

    1. Stop

      Whoever is holding the work files a change-request issue (the form is generated for them); PM records the change class as C. Nothing is built yet.

    2. Impact, not opinion

      The BA traces it: which capabilities and rules touch the window, which stories reference them, which tests assert it, what it does to support's current behaviour. The trace file is what makes this list mechanical rather than a guess.

    3. You decide

      Approve, reject, or approve a narrower version. The register gets a new entry with supersedes: pointing at the old one; history is append-only, so six weeks later you can still see what was believed before.

    4. Then the chain updates

      Requirement document, acceptance criteria, the affected stories, and the QA evidence plan. Where a rule contradicts confirmed content and the speaker cannot decide it, it goes back to being a question instead of a change.

    Phases 6 and 7 - ship it, then live with it

    The deployment gate closes like the others - evidence pack, phase-gate issue, your merge. What differs is where the work happens: deployment runs in CI behind the production Environment with you as required reviewer. vercel and supabase are denied twice over on a laptop, so "just push it quickly" is not available as a shortcut, which is the point.

    Operations is a phase, not an afterthought. /ops runs the rhythm: incidents, releases, health checks, stale-draft reporting, overdue questions. An emergency hotfix (class D) needs your authorisation, gets a post-hoc review within 24 hours, and forces a retro. Retros that find the harness at fault turn into proposals - /improve-harness writes the proposal, classifies it, and drafts the issue. It applies nothing.

    What the agents cannot do

    The concrete list, from the generated opencode.jsonc in this very project:

    BlockedLayerWhy it is there
    git push to main, --force, --delete, --mirror, reset --hard, clean, branch -D, filter-branchpermissions + policiesHistory rewriting is the one mistake you cannot review afterwards
    gh pr merge, gh pr review --approve, gh api, gh secret, gh variable, gh repo, gh release, gh workflowpoliciesAuthority verbs stay human. An agent that can approve its own review has no gate
    Any shell write: Set-Content, Add-Content, Out-File, Remove-Item, Move-Item, Copy-Item, New-Item, rm, del, mv, cppoliciesFile changes go through the audited edit tool, so "what changed" stays answerable
    Nested runtimes: pwsh, powershell, cmd, bash, wsl, sh, opencodepoliciesA shell is not a side door around the rules
    Publishing: npm publish, docker push, twine upload, cargo publish, plus this project's vercel and supabasepermissions + policiesArtifacts and environments ship through the pipeline or not at all
    Reading or writing .env*, *.pem, *.key, *.p12, *.pfx, .ssh/**, id_rsa*, id_ed25519*permissionsSecrets are not context. .env.example stays readable, deliberately
    Editing AGENTS.md, opencode.jsonc, .opencode/, .github/, harness/, docs/harness/permissionsAgents propose, the owner applies. This is the rule that stops governance drifting by degrees
    Delegating to the built-in general or explore agents, deeper than two levels, or carrying approval with a delegationpermissionsBuilt-ins inherit no role rules, so they are how a scoped agent becomes an unscoped one
    Loading a skill that project.yaml does not declarepermissions + validatorGrants are project configuration; an undeclared one fails the build rather than working quietly

    Configuration is not observation. Every row above is generated and statically checked - and none of it has ever been watched refusing a real request. The runtime matrix (N-01 to N-30, G-01 to G-04) has not been run, and the assumption that the policy layer is evaluated last is recorded in the ledger as designed. Until you run those cases, the honest sentence is: the harness is set up so that these things should stop, and your own approvals are the control that is known to work.

    Upgrading the harness later

    The instance carries its own copy of the kit, which is what makes this boring:

    pwsh -File harness/scripts/apply-harness-change.ps1 -DryRun    # what would change, file by file
pwsh -File harness/scripts/apply-harness-change.ps1 -Force     # timestamped backup, then regenerate
pwsh -File harness/scripts/validate-harness.ps1                # must still pass

    Only the generated set is rewritten - AGENTS.md, opencode.jsonc, the agents, commands, issue forms, workflows, governance files. Your requirements, decisions, knowledge and code are init-scope and never touched. Where you disagree with a generated rule, the path is a proposal upstream, not a local edit: a hand-patched instance is exactly the drift the kit exists to prevent.

    Where it cost time

    Not a sales page. What this project actually paid for:

    • The interview is 27 questions. Copying a starter config took eleven minutes; the interview took most of an afternoon, because a few answers (ID prefix, areas, what counts as a deploy CLI) needed a decision rather than a keystroke. Those are the right questions to answer once - they are just not quick.
    • Accepting staged knowledge is real work. The first /intake produced 31 items across four files and needed every one ticked. It got shorter after that, and the critic caught two overreaches and one missing answer on the first batch, which is what it is for.
    • Labels and Environments are on you. The taxonomy script is generated and the GitHub-side controls are documented, but nothing here can turn branch protection on for a repository it has no authority over.
    • You re-read what the agent wrote. Verdicts are advisory and requirements come with quotes; the first week felt slower than prompting freely, and that is the trade the harness is explicitly making.
