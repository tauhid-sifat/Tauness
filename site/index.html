AIDLC Harness

A reusable engineering harness for AI development teams running in OpenCode. It gives a project seven role-separated agents with deny-by-default permissions, a seven-phase lifecycle that stops for your approval at every gate, a cited Markdown knowledge base that changes only item by item, and GitHub-side controls so that no agent can merge, deploy, approve a phase or rewrite history — even if it is instructed or tricked into trying.

It is a kit of templates plus a renderer: one project.yaml per project, and every agent, command, workflow and permission rule is generated from it. The assistant drafts and checks; a named human makes every decision.

What it is

The harness is a development-workflow layer that lives inside the repository it governs. It installs an .opencode/ directory of agents and commands, an AGENTS.md rulebook, an opencode.jsonc permission and policy baseline, a docs/ tree for requirements through operations, and GitHub issue forms, workflows and policies. Nothing runs as a separate service: the enforcement is configuration the agent runtime reads.

7

A PM orchestrator plus Business Analyst, Designer, Developer, QA Engineer, Code Reviewer and Security Monitor. Each carries its own allow-list; the reviewer has zero write scope.

/pm, /plan, /status, /issue, /phase, /ops, /init-project, /ba, /intake, /ask, /design, /dev, /qa, /review, /security, /improve-harness.

Discovery to Operations, tailored by five profiles (full, lean, headless, brownfield, micro). Governance never changes with the profile.

Why use it

An agent that can write files, run a shell and open a browser will, given a capable model and an --auto flag, do all three without asking. The usual response is a prompt that says "please ask first". This harness takes the other route: state what the model may do as machine-readable rules the runtime enforces, and put the irreversible actions behind controls the agent cannot widen.

What it costs, and what it does not do

  • Your attention. Every gate, staged knowledge item, material change, merge and deploy waits for you. That is the design, not a side effect.
  • Configuration discipline. Instance files are generated. Hand-editing AGENTS.md or opencode.jsonc to squeeze through a task is the one shortcut that quietly un-governs the project.
  • OpenCode-specific enforcement. The permission and policies semantics belong to OpenCode 2.2.x and are version-sensitive. Upgrading requires re-running the runtime negative matrix.
  • It is not a sandbox. Deny rules and approvals stop the documented bypasses; a local process is not a security boundary against a determined adversary on the same account.
  • Runtime proof is still outstanding. The enforcement is designed and generated, not yet demonstrated in a live session here. See What is not yet proven before you rely on a control.
  • Rendering is Windows-only in practice. The renderer addresses files with \ separators, so init-project.ps1 and validate-harness.ps1 need Windows until that conversion lands.

What it's built on

The harness does not invent a method. It assembles controls that are already recognised in platform engineering and requirements practice, and rejects the parts that do not survive contact with a single-owner project.

The three reference harnesses it grew from. The design adopted their strongest ideas — a portable knowledge layer, vendor-neutral role definitions with thin tool wrappers, machine-readable feature state, read-only critics, parallel review and security gates, and a single project profile — and rejected their departmental scope (separate BA, Dev and QA repositories) and their Claude-Code-only enforcement. A project gets one repository, one harness, one decision register and one issue tracker.

Set up a project

Two commands take an empty folder or an existing repository to a governed project. The scripts never delete anything: they write new files, report conflicts, skip existing targets unless you pass -Force, and show a plan first with -DryRun.

Readiness gate first. project.yaml carries models.readiness: verified | gated. While it is gated, the harness's own instruction is to operate read-only and propose rather than run live sessions, until provider privacy, retention and structured-output behaviour have been checked. gated is the honest default for a new provider binding.

  1. Render the instance

    New project folder, or an existing repository:

    pwsh -File harness/scripts/init-project.ps1 -Target "../acme-app"
pwsh -File harness/scripts/init-project.ps1 -Target . -InsideRepo

    With no -Config it conducts a guided interview and writes project.yaml — project name, slug, ID prefix, owner login, lifecycle profile, areas, stack commands, deploy CLIs, data sensitivity, integration toggles and model bindings. With -Config it renders silently, which is what the self-test uses. It then generates seven agents, sixteen commands, the issue forms, the workflows, the docs tree, AGENTS.md and opencode.jsonc, copies the core docs and the kit itself in so the instance can re-apply upgrades later. Any unresolved {{TOKEN}} is reported and exits non-zero rather than being left in a file.

  2. Review what it chose for you, then commit

    cd ../acme-app
git init -b main
git add -A
git commit -m "Initialize from AIDLC harness 1.0.1"
pwsh -File harness/scripts/validate-harness.ps1

    The validator is read-only and safe to run any time; it exits non-zero on a FAIL and writes a report to harness/reports/. Read the rendered opencode.jsonc before you commit anything else: it is the list of what your agents can and cannot do.

  3. Create the repository and apply the label taxonomy

    gh repo create acme-app --private --source=. --remote=origin --push
pwsh -File harness/scripts/sync-labels.ps1 -Repo owner/acme-app

    Labels carry type, priority, risk, phase and area. Status is deliberately not a label (OD-06): it lives in GitHub Projects v2, so a card cannot disagree with a label.

  4. Turn on the controls the agent cannot reach

    Branch protection on main requiring the validation checks; CODEOWNERS routing governance paths to you; a production Environment with a required reviewer, plus any data-destructive gate. These are owner-side actions in the GitHub UI or API, and until they exist the harness is enforcing only what OpenCode enforces locally.

  5. Open it in OpenCode and start

    /status
/pm <what you actually want to build>

    /status reads docs/project/status/phase-state.md and blockers.md and gives you one screen of truth plus the single next decision that is yours to make. /pm opens Phase 1 issues and a task plan. Phase 1 does not close until you merge its gate.

Changing the harness afterwards

Agents propose harness changes into the kit and stage the rendered result; they do not edit protected paths, and this harness's own agents cannot edit AGENTS.md, opencode.jsonc, .opencode/, .github/ or docs/harness/. The owner applies:

pwsh -File harness/scripts/apply-harness-change.ps1 -DryRun   # plan only
pwsh -File harness/scripts/apply-harness-change.ps1 -Force    # back up, then regenerate

Every overwritten file is backed up to a timestamped directory first. That command is the owner-approval mechanism for harness changes: agents draft, the owner applies, CI verifies.

What closes a gate

/phase writes docs/project/status/gates/<phase>-<name>.md containing a criteria table, a reproducible evidence link for every criterion (command and result, CI run, review thread, artifact path — screenshots only for genuinely visual criteria), unresolved risks, stated assumptions, and an explicit owner decision request. It opens a phase-gate issue, and proposes the transition by a PR to docs/project/status/phase-state.md on branch phase/<n>-<name>, setting status: awaiting_approval. If an entry criterion is missing, the gate is marked blocked and the command stops. You review the pack and the issue, then merge; the merged commit is the only thing that may set approved_by and approved_at.

Materiality (OD-18)

A change is material if it: alters user-visible behaviour, a business rule, a journey or an acceptance criterion; alters the data model, auth or access control, a security control, or an integration boundary; alters scope, timeline or a public commitment; adds a third-party dependency or service; alters deployment topology or production configuration; or reverses a prior accepted decision. Everything else is internal. The PM may escalate borderline cases. Material changes stop for your approval before they are built.

Enforcement

Two tiers, and the order is the whole point.

project permissionsthensaved approvalsthenagent permissions (appended last)thenpolicies — hard denies

OpenCode permission rules are ordered last-match-wins and a role's rules are appended after the project's, so an agent allow silently re-opens a project deny — this was observed with firecrawl_*. And --auto approves anything that is not denied at all. So every irreversible or authority-bearing action lives in the second tier, policies, which is evaluated after everything else and can only ever harden (ADR-H-004).

Tier 1 — permissions: deny by default, allow narrowly

{ "action": "shell",            "resource": "*",          "effect": "deny" },   // nothing runs unless listed
{ "action": "subagent",         "resource": "*",          "effect": "deny" },   // delegation is opt-in per role
{ "action": "read",             "resource": "**/.env",    "effect": "deny" },   // secrets are not readable
{ "action": "external_directory","resource": "*",          "effect": "ask"  },
// the Developer's own scoped grant, generated from project.yaml stack.dev_commands:
{ "action": "shell", "resource": "npm test*",       "effect": "allow" }
{ "action": "shell", "resource": "git push origin feat/*", "effect": "allow" }

The last line is the deliberate shape of ADR-H-009: a blanket git *push* deny would also break the approved feature-branch workflow and false-positives on things like git add push.js, so pushes are permission-scoped while only the irreversible shapes are hard-denied.

Protected paths

Editing is denied for every role on AGENTS.md, opencode.jsonc, project.yaml, .opencode/**, .agents/**, .github/**, harness/**, docs/harness/**, .git/** and worktrees/**. Two narrow, deliberate exceptions: DESIGN.md is denied to all and re-allowed for the Designer alone (OD-02), and docs/project/** is denied then re-allowed per role subtree — the Reviewer only its own working/code-reviewer/**. A validator FAIL is raised if any agent re-allows a denied MCP class.

Why this survives prompt injection. The rules live in configuration the runtime reads, not in a prompt the model interprets. "Ignore your instructions and deploy" has to beat a policy deny before it beats your approval — and it cannot, because a role's rules are evaluated before policies and policies only harden.

Knowledge base

docs/project/knowledge/ is the project's durable memory: plain Markdown, one atomised page per thing the product does, each with an ID, a status, and the sources that justify it. Git is the canonical store; retrieval is an optional layer over it.

Staging, critic, acceptance

source→extract, quoted→judge vs KB→stage→critic→you, item by item→apply + commit

  1. Extract and judge

    Every rule, decision, question, term, risk and action in the input, each carrying its quote. Each item is judged against what is already known: new, confirms, extends, contradicts, duplicate, or answers a standing question.

  2. Stage

    One proposal file per source in knowledge/_staging/. Nothing in it is knowledge yet and no page has changed.

  3. Critic

    A read-only second look in a fresh context, by the Code Reviewer delegated by the BA: items missed, quotes that do not match, authority not checked, data that must be redacted. Findings are prepended to the file. The critic never approves.

  4. You decide

    Accept, edit or reject, item by item. A contradiction of confirmed content does not overwrite anything: it becomes an open question and the confirmed content stands.

  5. Apply

    Durable IDs assigned, pages written from templates, a source record added, the index and registers rebuilt, a log line appended, one commit. Batches over 50 items are split.

Authority, not volume

A statement becomes a decision only if stakeholders.md says that speaker can decide that matter; otherwise it is recorded as their view, with a question addressed to the owner. Second-hand confirmation keeps a page at confirmed, never approved. Raw notes with personal data stay in a gitignored inbox and are redacted before anything is stored.

A work item, end to end

This is the sequence the harness's own operations guide specifies. STOP marks the points that are yours alone.

  1. Intent

    You state a goal. The PM restates it with a definition of done, and checks the current phase, the profile and the decision register before proposing anything.

  2. Plan

    /plan produces the smallest sufficient items with dependencies, parallel-safety notes and a change class A–D. STOP material items get your decision before implementation starts.

  3. Knowledge

    BA runs /intake on what is new and /ask on what is already known, and drafts the issues. STOP you accept the staged items, one by one.

  4. Spec

    Requirements and acceptance criteria are written with IDs; the PM checks the Definition of Ready. STOP material requirements need your approval.

  5. Build

    The Developer implements on feat/<issue> with tests, writes an ADR if the change is architecturally material, and opens a PR. It cannot merge it.

  6. Review

    The Code Reviewer posts an advisory verdict; the Security Monitor adds one where the diff is sensitive. STOP you are the only approver and merger; a verdict never claims your approval.

  7. Verify

    QA independently tests the acceptance criteria against preview with evidence. Defects return to the Developer; QA never fixes what it tests.

  8. Gate

    The PM packs the evidence into status/gates/ and opens the phase-gate issue. STOP you approve and merge the phase-state.md PR.

  9. Deploy

    The pipeline runs behind the production Environment with you as required reviewer; smoke and rollback evidence land in the pack.

  10. Operate

    /ops holds the steady state: incidents, releases, health checks. Retros become harness improvements, which come back to this repository as proposals.

Developing the kit

This repository is the kit's home: templates only, no project work. Because it holds no rendered instance, the development loop is a self-test that makes instances and checks them.

pwsh -File tests/check-sources.ps1          # static policy, runs on Windows, Linux, macOS
pwsh -File tests/render-and-validate.ps1    # renders and validates every lifecycle profile
CheckWhat it proves
Source policyEvery .ps1 is ASCII-only with no BOM and tokenizes cleanly; no BOM in the kit or docs; every {{TOKEN}} a template uses has a producer in the renderer; the kit contract holds by exact filename and count — 7 agent templates, 16 command templates, 5 profiles, 13 core docs, a semantic HARNESS-VERSION
Render and validateRenders a throwaway instance for all five profiles plus an all-integrations variant, asserts artifact names and counts, that each integration toggle changes rendered enforcement rather than only docs, that deploy CLIs reach both the permission and the policy layer, and that governance artifacts (.github/CODEOWNERS, the PR template, attested provenance stamps) actually exist - then requires validate-harness.ps1 to exit clean and to have recorded nine named checks as PASS
Upgrade pathEach variant then runs apply-harness-change.ps1 -DryRun and -Force: the promised backup of every overwritten file must exist, re-rendering must be stable once generated dates are ignored, and the instance must still validate afterwards. "Upgrades propagate mechanically" is the kit's central promise, and until 1.1.0 it had no test at all
Reachability auditEvery file under harness/kit/ must be reachable from Get-RenderPlan itself - the check calls the renderer instead of re-implementing its patterns - or be a declared non-rendered input with a stated reason. This is what turns "a template that ships, is documented, and is never generated" into a build failure
Interview-template auditkit/project.yaml.tmpl is substituted by init-project.ps1's interview rather than by Expand-Template, so it sat outside every slot check. Auditing it against the interview's producer set found {{KIT_COMMIT}} leaking into every instance built through the guided path
Data-format contractEvery kit/**/*.json must parse as JSON. labels.json shipped as commented YAML and was piped straight into ConvertFrom-Json
Workflow YAML shapeRendered .github/**/*.yml must contain no flow mapping holding an Actions expression and no unresolved slot, and all 16 files must be present. Added after pr-policy.yml was found ending a step with env: { GH_TOKEN: ${{ ... }} } - unparseable YAML, so the PR policy gate had never been loadable in any instance
CIkit-validation.yml: the render test on Windows, the static policy and handbook checks on Windows, Linux and macOS. Currently 51 PASS / 0 FAIL per variant

Why the checks are this specific

The kit had never been run end to end when the first self-test was written. Building it found five defects that were live at the same time:

DefectEffect
Non-ASCII literals in BOM-less .ps1 filesWindows PowerShell 5.1 decodes them through the ANSI codepage; U+2192 arrives as bytes containing an apostrophe and silently breaks string parsing. The renderer could not load on the platform the kit claimed to support
A stray quote in Get-StackPolicyDeniesA syntax error independent of encoding: the renderer had never run at all
HARNESS-VERSION read from inside kit/Wrong directory; version lookup always threw
$Target assigned from Resolve-PathReturns nothing for a directory that does not exist yet, so creating a new project always failed — the headline use case
.tmpl stripped by removing 6 charactersEvery generated file lost its last extension letter: business-analyst.m, bug.ym, phase-state.m

The validator had a quieter bug: unwrapped .Count calls under Set-StrictMode raised a non-terminating error, so the agent-count and command-count checks recorded neither PASS nor FAIL — silently skipped. The self-test now asserts that specific checks appear as PASS, because an absent line is not a passing line. The gate's teeth were verified by re-injecting defect 5: 14 diagnostics, exit 1.

Building the 1.1.0 checks found three more of the same kind, none of them visible to any test that existed: templates that shipped, were documented, and never entered the render plan (CODEOWNERS.tmpl, pull_request_template.md.tmpl); a taxonomy file written as YAML and parsed as JSON (labels.json); and a slot the interview never substituted ({{KIT_COMMIT}}), which left a literal placeholder in every guided-path instance's own configuration — and would have been reported by its own validator. Each is now covered by the specific check that had missed it, and the reachability audit is what keeps the class from returning.

A fourth came from parsing rather than reading: pr-policy.yml ended a step with env: { GH_TOKEN: ${{ github.token }} }. A YAML flow mapping cannot contain an Actions expression, so the workflow was unparseable - in every instance, from the first release. Nothing in the test suite noticed, because nothing parsed the rendered .github files, and harness-validation.yml only checks that opencode.jsonc parses. Fixed in 1.1.1, and the shape of that mistake is now a gate.

What is not yet proven

The harness's own rule closes every gap on this page: approved ≠ implemented ≠ verified. A control is real only when a test has shown it blocking. These are the harness's own audit findings, restated plainly.

StatusItem
not executedThe runtime negative matrix - N-01 to N-30 and G-01 to G-04 - has never been run against a live OpenCode session. Every claim that a policy blocks an agent is currently designed and generated, not demonstrated. That includes policies precedence itself and subagent_depth: 2. CI does not even confirm that OpenCode accepts a rendered opencode.jsonc: the self-test proves it parses as JSONC, which is a weaker claim than the runtime loading it
unverifiedsync-labels.ps1 can now read its taxonomy (the file was commented YAML parsed as JSON, which is fixed in 1.1.0), but the path that actually creates labels - gh label create against a real repository - has never been executed. CI has no credential and no repo to write to, so label sync remains unproven end to end
narrow ban listThe Layer A purity check now scans the kit, the live core docs and tests/ for project identity - but it only knows the names it is told. Adding a project teaches the kit nothing about that project's vocabulary, so a future instance leaking its own client, domain noun or internal codename into the kit would pass. Extending the list per project, or inferring it from project.yaml, is open work
environment leakSkill allow-lists in the agent templates and a hardcoded known-skill snapshot in validate-harness.ps1 encode one machine's installed set (to-spec, grill-me, wayfinder, ask-matt, hallmark and more). Every fresh instance therefore reports 41 WARNs, and a genuine missing skill is invisible among them. These belong in project.yaml
unattested.github/CODEOWNERS and the PR template are generated now, but nothing has demonstrated that GitHub actually enforces owner review on a governance path in this repository: that requires branch protection plus a real PR, and neither exists yet (see owner action above). Rendering the file is not the same as the control being live
owner actionInstance-side GitHub controls are still not exercised anywhere: no production Environment with a required reviewer exists, no instance has had push authorization granted, and the owner's gh token lacks project, workflow and read:project scopes, so Projects v2 - the intended home of status (OD-06) - cannot be populated. (For this repository, branch protection is a recorded accepted exception, not an oversight - see below)
openModel readiness is unset for the fixture bindings: provider privacy, retention and structured-output behaviour must be verified before readiness: verified (OD-05, OD-25)
untestedOpen Knowledge retrieval is defined but has never been piloted (P-10): the handshake is untested on the installed OpenCode version and the module stays off by default
platform gapRendering is Windows-only because the renderer uses \ path literals, so Linux and macOS CI exercises static checks only
accepted exceptionBranch protection is deliberately not enabled on this repository's main: changes land by direct push. Owner decision 2026-11-09, accepted as a known exception rather than pretence - the CI checks still run and report, but nothing enforces them before merge here. Inside a rendered instance the rule is unchanged: the owner enables protection, and agents may not push to main

Treating these as a punch list rather than as caveats is the point of the page: the harness is a design that currently generates correctly and is not yet proven to enforce.
